# Входы, собственные корни и сеть серверов

Статус: уточнение направления владельцем 22.10.2026 и план следующих пакетов.
Это не описание уже реализованного импорта, социальных записей или федерации.
Текущий работающий сервер предоставляет аккаунты, приветствия сайтов,
публичную проекцию корней и read-only full iframe/bridge.

## 1. Четыре разные сущности

| Сущность | Что определяет | Чего не создаёт автоматически |
|---|---|---|
| Экземпляр сервиса, сервер-узел | Свои API, БД, учётные записи и расчёт влияния | Общую БД с другими серверами |
| Вход/сайт (`s_…`) | Приветствие, стартовую навигацию, тему, подключённые источники | Новый аккаунт, отдельную массу голосов или изолированный граф |
| Git-источник | Версионируемые Markdown-корни и их происхождение | Право менять чужие точки или выполнять код на сервере |
| Пользователь | Авторство, собственные точки и действия в экземпляре | Обязанность иметь сайт или владеть репозиторием |

`wiki.geno-dice.com` работает как самостоятельный hosted-вход. Его регистрация
через `/sites/` полезна: она закрепляет приветствие и происхождение сайта в общей
БД. Сгенерированные iframe и bridge URL — дополнительные варианты подключения,
а не обязанность встраивать iframe в собственную hosted-копию.

Текущая настройка `NODE06_DEFAULT_SITE_ID` выбирает активное приветствие для `/`
этого экземпляра. Она не создаёт новый сервер, источник корней или локализацию.
Не менять существующий ID только потому, что его iframe не используется.

## 2. Своя коренная вики для каждого входа

**Требование владельца:** форк/подключённый Git-источник может задавать собственный
набор корней и стартовую страницу, а не только дополнения к обязательной общей
главной странице. Возможные представления: облако понятий, карта, индекс/список
ссылок на редактируемые посты, справочник или вики-форум.

Neocities NODE06: более атмосферный, неформальный вход в публичные фрагменты лора.
Geno-Dice Wiki: сдержанное описание игр, справка и обсуждения без лишних подробностей.
Это редакционный выбор входа, а не разные языковые версии или разные БД.
RU/EN и любые другие языки остаются независимыми точками общего пространства.

**Предложение реализации для P04/P08:** профиль входа выбирает домашнюю точку,
подключённые root sources и начальный вид/набор стартовых ссылок. Эти настройки
не изменяют содержимое/ID чужих точек, ACL, глобальный поиск или бюджет влияния.
Скрытая из стартового облака точка не удаляется из общей БД. При переходе к общей
точке сохраняется текущая оболочка; явный переход к другому входу меняет оболочку.
Облако — способ показать ссылки, не новая формула социальных координат.

Git source proof, manifest, immutable SHA, preview/accept, namespaces и безопасное
отключение принадлежат [ROOT-IMPORT-V1](ROOT-IMPORT-V1.md). Для первого безопасного
импорта сохраняется opt-in `site-content/`: копия upstream `content/` не становится
вторым набором тех же глобальных точек. Собственные корни получают source/site
namespace; это позволяет построить собственную главную, не перезаписывая `core`.
В первом ROOT-IMPORT контракте — один зарегистрированный Git-source на сайт,
namespace принадлежит сайту. Профиль может показывать публичные sources разных
сайтов, не присваивая права на них. Несколько независимых sources под одним site
namespace требуют отдельного расширения ID-контракта; не добавлять их молча.
Смена владельца/ветки/источника не переназначает существующие посты и поддержку.

Выборочное отображение **не является приватностью**. Публичный Git, история
коммитов, API и прямые ссылки доступны независимо от стиля/обнаружимости входа.
В публичные источники попадают только разрешённые к публикации фрагменты;
авторские секреты не публикуются под видом «потайного» интерфейса. Более строгие
права редактирования справочных источников не превращают соседние пользовательские
мнения в канон и не позволяют голосованию автоматически менять канон.

## 3. Пользователь без сайта

**Требование владельца:** любой зарегистрированный пользователь экземпляра может
создавать новые точки и голосовать через все подключённые к этому экземпляру
входы. Собственный сайт, Git-форк, site claim и роль владельца сайта не требуются.
Проверка сайта требуется оператору входа, а не каждому его посетителю.

Права задают аккаунт, авторство, явные роли и серверные ограничения; оформление
или подборка корней не являются разрешением/запретом на авторство. Пользователь
редактирует свои посты, но не Git-корни, принадлежащие другому источнику. Одно
действие над общей точкой имеет один результат во всех входах: повтор того же
голоса через другой сайт не выдаёт дополнительный голос или массу. Прямой вход
на hosted UI также работает без наличия собственного сайта.

Это требование к P03 scoped consent/P05 CRUD и реакциям/P06 расчёту/P08 интерфейсам.
Сегодня bridge публичный read-only: нельзя выдавать его за готовую запись.
Страница Neocities не получает пароль, аварийный код или глобальную сессию;
будущие записи идут через узкие grants/consent и проверяются сервером. Пока
предоставлены только аккаунты, приветствия владельцев и публичные чтения.

## 4. «Файловый API» и веб-API

Да, это два канала работы с одним движком:

- Git/Markdown → проверяемый импорт корней → ревизии/ссылки/происхождение в БД;
- HTTP API → пользовательские посты, правки, реакции → те же общие сущности.

Файловый канал не означает произвольную запись файлов на сервере или выполнение
`build.py`/JS из присланного форка. Веб-правка не переписывает Git-источник. Source
authority, редактор и маршрут исправления видны пользователю. Импорт новой ревизии
подчиняется тому же требованию уведомить поддержавших об изменении смысла; нельзя
сохранить старую поддержку при замене утверждения. Первый importer ограничен
зарегистрированными публичными GitHub-источниками; поддержка других Git-hosts
требует отдельного fetch/SSRF/auth контракта. Возможность **деплоить** из Gitea-копии
не означает, что публичный **импортер контента** уже умеет читать любой Git-host.

## 5. Независимые серверы и внешние точки

**Требование владельца:** движок можно независимо развернуть из копии репозитория.
У каждого сервера своя БД/регистрация, а публичные точки разных серверов могут
ссылаться друг на друга. Это расширение прежней модели «один сервис»; общий граф
и единый бюджет внутри экземпляра сохраняются.

**Предложения, требующие отдельного контракта:**

- Для адресации различать локальный ID и экземпляр-источник. Пара
  `(instance_id, point_id)` — кандидат глобальной идентичности; формат стабильного
  instance ID, ссылки на ревизии и миграция домена пока не утверждены.
- Первый внешний режим — явная ссылка на публичную точку другого сервера с
  обозначением источника. Она не копирует чужой текст/авторство, не создаёт
  гарантированную обратную связь и не объединяет социальную геометрию/голоса.
- Обычные HTTPS-ссылки можно публиковать уже сейчас. Они ещё не федеративное ребро
  графа. Автопревью, обход внешнего графа и импорт снимков требуют отдельной защиты
  SSRF, лимитов, проверки происхождения/версии и обработки недоступности.
- Удалённый сервер, внешний hostname или одноимённый пользователь не получает
  локальных прав, cookie, паролей или возможности голосовать от чужого имени.

### Решение владельца: отдельные регистрации и влияние

**Подтверждено 22.10.2026:** на независимых серверах регистрируются отдельно;
влияние между ними не переносится. Ссылаться и подписываться можно на публичную
точку любого домена. Возможность синхронизировать аккаунты между доверяющими
серверами нужно предусмотреть, но она не означает общую БД влияния.

Вики на одной БД уже используют общие аккаунты; между такими входами отдельная
синхронизация не требуется. Межсерверная синхронизация — полномочие операторов
независимых экземпляров. Одно лишь подтверждение владения сайтом/Neocities-origin
не разрешает репликацию пользователей сервера или подключение к PostgreSQL.

### Внешние подписки — требования и предложение реализации

- Подписка — сохранённый интерес/наблюдение, **не голос**, доверие или передача
  влияния. Для сохранения подписки достаточно аккаунта на своём сервере; аккаунт
  на сервере публичной целевой точки не требуется.
- Подписки и обычные ссылки не ограничены кругом серверов, согласившихся на
  account sync. При невозможности автоматически читать целевой сервис ссылка
  сохраняется с явным статусом, без выдуманных обновлений.
- Предлагается хранить цель по квалифицированному instance/point ID, исходному
  URL и известной ревизии; до утверждения discovery/URI-контракта это не готовая
  схема. На своём сервере хранится подписка, у источника остаётся сама точка.
- Обновления показывают источник, смену ревизии и недоступность. Получение
  обновления не подтверждает согласие пользователя с новым смыслом и не меняет
  старые голоса. Перестать следить можно локально, без разрешения чужого сервера.
- Для первого сетевого пакета предлагается опрос публичных данных с лимитами,
  backoff и дедупликацией. Уведомления/webhooks — отдельное расширение с проверкой
  отправителя. Не передавать удалённому сайту локальную сессию или список
  подписчиков без отдельного действия/разрешения.
- Для правки/голоса на другом сервере нужны его локальная авторизация и ACL.
  Подписка или связанный профиль сами по себе их не дают. Локальная запись
  интереса/обсуждение внешней ссылки не меняет голосование на сервере-источнике.
- Любой домен — не право на произвольный исходящий HTTP-запрос из backend:
  resolver/fetch должен отвергать private/link-local/loopback/mixed DNS, проверять
  TLS/redirects, ограничивать размер/время/переходы и оставлять обычную ссылку при
  неподдерживаемом протоколе. Произвольные HTML/скрипты не исполняются.

### Синхронизация аккаунтов доверенных серверов — границы проекта

**Требование утверждено:** предусмотреть opt-in синхронизацию пользовательских
аккаунтов между доверяющими экземплярами. **Следующие детали — предложение,
подлежащее отдельному review перед реализацией**, а не уже открытый API:

1. Начать со связи локальных аккаунтов и репликации разрешённой проекции профиля,
   а не полного копирования таблиц. У каждого сервера остаётся свой локальный
   user ID, состояние аккаунта и механизм входа. Связь опирается на подтверждённый
   `(issuer_instance_id, subject_user_id)`, не на совпадение ника/аватара.
2. Операторы с обеих сторон явно настраивают доверие, направление, ключи, список
   разрешённых полей и лимиты. Автоматического транзитивного доверия нет:
   A доверяет B, B доверяет C не означает разрешение C менять пользователей A.
3. Пользователь подтверждает связь/передачу выбранных полей. Возможность будущего
   входа по подтверждению доверенного сервера отдельно разрешается принимающим
   экземпляром и пользователем; это не обязательный глобальный SSO для всех.
   Принимающий сервер может предложить создание/активацию локального аккаунта,
   но не активирует голосующего пользователя из фоновой копии профиля.
4. Предложенный allowlist: публичное имя/описание и подтверждённая связь профилей;
   точный набор и направление разрешения конфликтов утвердить отдельно. Пароли
   и их хеши, аварийные коды/секреты, cookies, токены сессий/CSRF/embed, приватные
   поля не реплицируются. Права администратора/модератора, владение сайтами и
   Git-источниками остаются локальными, а не наследуются из чужого профиля.
5. Влияние, доверие, голоса, распределения, социальные координаты и их история
   не входят в account sync. Локальная активация подчиняется правилам этого
   сервера; импорт каталога профилей не увеличивает число активных участников
   или массу. Связывание уже существующих аккаунтов не суммирует их бюджеты и
   требует явного разбора конфликтующих локальных голосов до объединения.
6. Синхронизация использует отдельные узкие server-to-server сообщения с проверкой
   источника, схемы, срока/повтора и аудита; не прямой доступ соседнего сервера к
   БД и не универсальный экспорт пользователей. Протокол/криптографические детали
   проектируются и проверяются отдельно; не писать самодельную схему в этом ADR.
7. Нужны provenance и field ownership, идемпотентность, монотонные версии/решение
   конфликтов, offline/retry и ограничения объёма. Полученный профиль никогда не
   перезаписывает локальные credentials или не захватывает одноимённый аккаунт.
8. Доверие и связь отзываются. Отзыв прекращает будущую синхронизацию/делегированный
   вход, не удаляет самостоятельно локальные посты/голоса/сохранённые подписки и
   не отключает независимый локальный способ входа. Пользователь видит состояние
   связи и может сохранить локальный пароль/аварийное восстановление.

Так сеть имеет три независимо разрешаемые возможности: публичные ссылки,
подписки на точки и доверенную синхронизацию аккаунтов. Первая не требует второй,
а первые две не требуют доверия для синхронизации пользователей. Ничто из этого
не переносит влияние между серверами.

## 6. Порядок работы и приёмка

1. Завершить текущий onboarding wiki/Neocities и real-origin bridge/full acceptance.
   Существующий `s_` остаётся; hosted `/` привязать к его активному приветствию.
2. P04: безопасный root importer, отдельные source-наборы и стартовая подборка;
   P08: облако/индекс как режим входа с общим поиском и переходами.
3. P03/P05/P06/P08: пользовательские точки и голоса без владения сайтом,
   уведомления о смене ревизии, scoped embed writes и единый расчёт внутри БД.
4. Отдельный пакет сети серверов: утвердить идентичность/URI/ссылки/подписки,
   затем отдельно схему opt-in синхронизации аккаунтов/доверия;
   затем испытать два независимых экземпляра. Ни одна общая БД не мигрирует и не
   разделяется автоматически ради этого уточнения плана.

Обязательные сценарии для продолжения другим агентом:

| Сценарий | Ожидаемый результат |
|---|---|
| Два входа одной БД с разными root sources | Разные старты и стиль, общие публичные точки доступны по ссылке/поиску |
| Одинаковый локальный slug в источниках двух сайтов | Разные namespaced ID, никаких перезаписей |
| Аккаунт без сайта создаёт пост и голосует через два входа | Один автор/пост и один голос над общей точкой |
| Попытка такого пользователя править чужой Git-корень | Отказ с указанием владельца/канала правки |
| Отключение источника/смена корней главной | Пользовательские посты, история и поддержка не удалены |
| Более скрытое оформление Neocities | Не обещает конфиденциальности публичного содержания |
| Ссылка между двумя серверами | Видны источник и граница; нет автоматических прав/переноса голоса |
| Подписка на публичную точку недоверенного сервера | Работает как сохранённый интерес без его аккаунта, cookie и голосов |
| Фоновая синхронизация профилей доверенного сервера | Не создаёт активных голосующих, локальных админов или дополнительную массу |
| Совпали ники двух пользователей | Нет автоматического слияния; требуется подтверждённая связь identities |
| Повтор/устаревшая версия/транзитивно доверенный источник | Нет чужой перезаписи или расширения scope; событие отклонено/идемпотентно |
| Отзыв доверия | Синхронизация прекращена, локальное авторство/вход/подписки сохранены |
| Удалённая точка недоступна или изменилась | Явное состояние/пин ревизии по утверждённому контракту; без тихой подмены |

Эта запись не вводит новые endpoints/таблицы/миграции. До реализации составить
конкретную схему и API в соответствующем пакете, обновить независимые клиентские
контракты и не помечать требования реализованными по одному изменению плана.
